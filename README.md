# Архітектура та проєктна схема графа для кінорекомендаційної системи(Neo4j)

Цей документ описує концептуальну та фізичну модель графа, спроєктовану за принципом **Query-first design**, а також містить відповіді на ключові архітектурні запитання.

---

## 1. Візуальна схема графа(ASCII-діаграма)

```text
       ┌──────────┐
       │   User   │
       └────┬─────┘
            │
            │ [:RATED {rating: 5, timestamp: 1672531200}]
            ▼
      ┌───────────┐               ┌───────────┐
      │   Movie   │─────────────▶ │   Genre   │
      └───────────┘ [:HAS_GENRE]  └───────────┘
```

---

## 2. Відповіді на ключові архітектурні запитання

### 1. Які сутності стали вузлами, а які - ребрами? Чому?
* **Вузли(`User`, `Movie`, `Genre`)** - це незалежні доменні сутності(First-class entities), які мають власні унікальні ідентифікатори, багаторазово перетинаються та є точками входу(`MATCH` з індексами) для пошукових запитів.
* **Ребра(`RATED`, `HAS_GENRE`)** - це динамічні зв'язки або атрибутивні відношення між сутностями. Вони описують *як саме* сутності взаємодіють одна з одною, утворюючи основу для графового обходу(Index-Free Adjacency).

---

### 2. Оцінка користувача за фільм - це ребро `(User)-[:RATED]->(Movie)` чи окремий вузол `(Rating)`? Аргументуйте своє рішення.

У даній архітектурі оцінка реалізована як **властивість ребра `[:RATED]`**. Ось детальний аналіз плюси/мінуси:

* **Варіант А: Оцінка як ребро з властивостями `(User)-[:RATED {rating, timestamp}]->(Movie)`(Обраний підхід)**
  * **Плюси:** * Максимальна продуктивність(Query-first). Пошук рекомендацій на основі спільного кола інтересів(Collaborative Filtering) виконується через пряме з'єднання двох вузлів. Базі не потрібно робити додатковий стрибок(hop) у пам'яті через проміжний вузол, що вдвічі зменшує кількість `db hits`.
    * Економія простору в оперативній пам'яті(RAM) та на диску.
  * **Мінуси:**
    * Обмеженість бінарного зв'язку. Якщо у майбутньому знадобиться зробити оцінку повноцінною сутністю(наприклад, щоб інші користувачі могли ставити лайки на самі коментарі/оцінки, або прив'язати до оцінки мультимедійний відгук), ребро доведеться рефакторити у проміжний вузол.

* **Варіант Б: Оцінка як окремий вузол `(User)-[:WROTE]->(Rating)-[:FOR]->(Movie)`**
  * **Плюси:** * Гнучкість(N-арні зв'язки). Дозволяє легко розширювати модель додатковими зв'язками до оцінки(наприклад, `(Rating)-[:VOTED_HELPFUL]->(OtherUser)`).
  * **Мінуси:** * Катастрофічне зростання кількості вузлів(у мільйонній базі з'явиться десятки мільйонів додаткових вузлів-оцінок). 
    * Збільшення глибини шляху при обходах графа, що різко знижує швидкість виконання рекомендаційних алгоритмів у реальному часі. Критичне збыльшення `db hits`

### 3. Чому жанри фільму вигідніше зберігати як окремі вузли `(Genre)`, а не як список у властивості вузла `Movie`?

Зберігання жанрів у вигляді масиву рядків у властивості вузла(наприклад, `Movie {genres: ['Action', 'Comedy']}`) є реляційним антипатерном у світі графів. Використання окремих вузлів `(Genre)` має такі переваги:

1. **Швидкість фільтрації та рекомендацій:** Запит на кшталт *«Знайти всі фільми в жанрі Action, які дивилися мої друзі»* у разі окремих вузлів виконується через нативний обхід ребер `(User)-[:FRIENDS]->()-[:RATED]->(Movie)<-[:HAS_GENRE]-(Genre {name: 'Action'})`. Якщо жанри загорнуті у масив властивості, базі доводиться постійно парсити і сканувати внутрішні структури рядків для кожного фільму, що вбиває продуктивність індексів.
2. **Масштабованість і глобальний аналіз:** Окремі вузли дозволяють запускати алгоритми машинного навчання(наприклад, аналіз спільнот, метрики схожості категорій) безпосередньо через графові проєкції.
3. **Цілісність даних:** Уникнення опечаток. У випадку масивів одне й те саме слово в різних фільмів може бути записане як `"Sci-Fi"`, `"SciFi"` або `"Science Fiction"`. Вузел-довідник `(Genre)` гарантує єдине джерело правди для кожної категорії.

## Завдання 2: Завантаження великих обсягів даних(ETL-процес)

Усі Cypher-запити збережено у файлі `part2_load.cypher`. Нижче наведено архітектурне обґрунтування кожного етапу завантаження.

### 1. Завантаження вузлів(Users та Movies)
Для ідемпотентності(захисту від дублювання) використовується команда `MERGE` замість `CREATE`. 

* **Users:** `MERGE` виконується виключно за унікальним ключем `userId`(попередньо приведеним до `Integer`, оскільки з CSV все читається як рядки). Додаткові властивості(стать, вік) встановлюються через `ON CREATE SET`, щоб не перезаписувати їх даремно при повторному запуску скрипту.
* **Movies & Genres:** Жанри у датасеті MovieLens приходять як один рядок з роздільником(наприклад, `Action|Adventure`). Ми використовуємо функцію `split()` та `UNWIND`, щоб перетворити цей рядок на масив і розгорнути кожен жанр в окремий рядок. Після цього робимо `MERGE` для вузла `Genre` і відразу створюємо зв'язок `(Movie)-[:HAS_GENRE]->(Genre)`. Це реалізує нашу Query-first схему.

### 2. Створення індексів(До завантаження ребер)
```cypher
CREATE INDEX user_id_index IF NOT EXISTS FOR(u:User) ON(u.userId);
CREATE INDEX movie_id_index IF NOT EXISTS FOR(m:Movie) ON(m.movieId);
```
