# Архітектура та проєктна схема графа для кінорекомендаційної системи(Neo4j)

Цей документ описує концептуальну та фізичну модель графа, а також містить відповіді на ключові архітектурні запитання.

---

## 1. Візуальна схема графа

```text
       ┌──────────┐
       │   User   │
       └────┬─────┘
            │
            │ [:RATED {rating: 5, timestamp: 1672531200}]
            ▼
      ┌───────────┐               ┌───────────┐
      │   Movie   │─────────────▶ │   Genre   │
      └───────────┘ [:HAS_GENRE]  └───────────┘
```

## 2. Відповіді на ключові архітектурні запитання

### 1. Які сутності стали вузлами, а які - ребрами? Чому?
* **Вузли(`User`, `Movie`, `Genre`)** - це незалежні данні(сутності), які мають власні унікальні ідентифікатори, багаторазово перетинаються та є точками входу(`MATCH` з індексами) для пошукових запитів.
* **Ребра(`RATED`, `HAS_GENRE`)** - це динамічні зв'язки або атрибутивні відношення між сутностями. Вони описують *як саме* сутності взаємодіють одна з одною, утворюючи основу для графового обходу.

---

### 2. Оцінка користувача за фільм - це ребро `(User)-[:RATED]->(Movie)` чи окремий вузол `(Rating)`? Аргументуйте своє рішення.

У даній архітектурі оцінка реалізована як **властивість ребра `[:RATED]`**. Ось детальний аналіз плюси/мінуси:

* **Варіант А: Оцінка як ребро з властивостями `(User)-[:RATED {rating, timestamp}]->(Movie)`(Обраний підхід)**
  * **Плюси:** Максимальна продуктивність. Пошук рекомендацій на основі спільного кола інтересів виконується через пряме з'єднання двох вузлів. Базі не потрібно робити додатковий стрибок у пам'яті через проміжний вузол, що вдвічі зменшує кількість `db hits`.
    * Економія простору в оперативній пам'яті та на диску.
  * **Мінуси:**
    * Обмеженість бінарного зв'язку. Якщо у майбутньому знадобиться зробити оцінку повноцінною сутністю(наприклад, щоб інші користувачі могли ставити лайки на самі коментарі/оцінки, або прив'язати до оцінки мультимедійний відгук), ребро доведеться рефакторити у проміжний вузол.

* **Варіант Б: Оцінка як окремий вузол `(User)-[:WROTE]->(Rating)-[:FOR]->(Movie)`**
  * **Плюси:** Гнучкість. Дозволяє легко розширювати модель додатковими зв'язками до оцінки(наприклад, `(Rating)-[:VOTED_HELPFUL]->(OtherUser)`).
  * **Мінуси:** Досить швидке зростання кількості вузлів(у мільйонній базі з'явиться десятки мільйонів додаткових вузлів-оцінок). 
    * Збільшення глибини шляху при обходах графа, що різко знижує швидкість виконання рекомендаційних алгоритмів у реальному часі. Критичне збыльшення `db hits`

### 3. Чому жанри фільму вигідніше зберігати як окремі вузли `(Genre)`, а не як список у властивості вузла `Movie`?

Зберігання жанрів у вигляді масиву рядків у властивості вузла(наприклад, `Movie {genres: ['Action', 'Comedy']}`) є реляційним антипатерном у світі графів. Використання окремих вузлів `(Genre)` має такі переваги:

1. **Швидкість фільтрації та рекомендацій:** Запит типу *«Знайти всі фільми в жанрі Action, які дивилися мої друзі»* у разі окремих вузлів виконується через обхід ребер `(User)-[:FRIENDS]->()-[:RATED]->(Movie)<-[:HAS_GENRE]-(Genre {name: 'Action'})`. Якщо жанри загорнуті у масив властивості, базі доводиться постійно парсити і сканувати внутрішні структури рядків для кожного фільму, що вбиває продуктивність індексів.
2. **Масштабованість і глобальний аналіз:** Окремі вузли дозволяють запускати алгоритми машинного навчання(наприклад, аналіз спільнот, метрики схожості категорій) безпосередньо через графові проєкції.
3. **Цілісність даних:** Уникнення опечаток. У випадку масивів одне й те саме слово в різних фільмів може бути записане як `"Sci-Fi"`, `"SciFi"` або `"Science Fiction"`. Вузол-довідник `(Genre)` гарантує єдиний словник для кожної категорії.

## Завдання 2: Завантаження великих обсягів даних

Усі Cypher-запити збережено у файлі `part2_load.cypher`. Нижче наведено архітектурне обґрунтування кожного етапу завантаження.

### 1. Завантаження вузлів(Users та Movies)
Для захисту від дублювання використовується команда `MERGE` замість `CREATE`. 

* **Users:** `MERGE` виконується виключно за унікальним ключем `userId`(попередньо приведеним до `Integer`, оскільки з CSV все читається як рядки). Додаткові властивості(стать, вік) встановлюються через `ON CREATE SET`, щоб не перезаписувати їх даремно при повторному запуску скрипту.
* **Movies & Genres:** Жанри у датасеті MovieLens приходять як один рядок з роздільником(наприклад, `Action|Adventure`). Ми використовуємо функцію `split()` та `UNWIND`, щоб перетворити цей рядок на масив і розгорнути кожен жанр в окремий рядок. Після цього робимо `MERGE` для вузла `Genre` і відразу створюємо зв'язок `(Movie)-[:HAS_GENRE]->(Genre)`. Це реалізує нашу Query-first схему.

### 2. Створення індексів(До завантаження ребер)
```cypher
CREATE INDEX user_id_index IF NOT EXISTS FOR(u:User) ON(u.userId);
CREATE INDEX movie_id_index IF NOT EXISTS FOR(m:Movie) ON(m.movieId);
```

## Завдання 3: Аналітичні та рекомендаційні Cypher-запити

Усі запити збережено у файлі `queries/part3.cypher`.

### Пояснення логіки запитів

1. **Запит 1(Фільми жанру Thriller з рейтингом > 4.0):**
   * Спочатку фільтруємо вузли за індексом жанру `(g:Genre {name: 'Thriller'})`.
   * Збираємо всі оцінки `RATED` для знайдених фільмів і агрегуємо середнє значення `avg(r.rating)` через конвеєр `WITH`.
   * Фільтрація `WHERE avg_rate > 4.0` виконується після агрегації(аналог `HAVING` в SQL).

2. **Запит 2(Активні ценителі 5-зіркових фільмів):**
   * Шукаємо лише ті ребра `RATED`, де значення властивості `rating` дорівнює `5.0`.
   * Групуємо за користувачем `u`, підраховуємо кількість `count(r)` і залишаємо лише тих, у кого лічильник перевищує 50.

3. **Запит 3(Спільні високооцінені фільми для двох користувачів):**
   * Використовуємо графовий шаблон `(User1)-[:RATED]->(Movie)<-[:RATED]-(User2)`. 
   * Це дозволяє знайти перетин інтересів двох конкретних сутностей без виконання важких SQL `JOIN` операцій.

4. **Запит 4(Стабільні жанри-лідери):**
   * Обєднуємо дані на рівні вузла `Genre`.
   * Додаємо поріг `WHERE rate_cnt >= 100`, щоб відсіяти статистичний шум(наприклад, маловідомий жанр з однією оцінкою 5.0, який фальшиво очолить рейтинг).

5. **Запит 5(Коллективний досвід):**
   * **Крок 1:** Знаходимо "схожих користувачів"(`other`), які високо оцінили ті ж фільми, що й цільовий `userId: 1`.
   * **Крок 2:** Знаходимо фільми `rec`, які оцінили ці схожі користувачі.
   * **Крок 3:** Відсікаємо фільми, які цільовий користувач вже дивився(`NOT(u)-[:RATED]->(rec)`).
   * **Крок 4:** Сортуємо результати за кількістю збігів серед схожих користувачів(`score`) та середнім рейтингом.

6. **Запит 6(Найкоротший шлях між користувачами):**
   * Використовуємо алгоритм `shortestPath`, який шукає найкоротшу топологічну відстань в пам'яті через будь-яку кількість ребер `RATED`(обмежено діапазоном `*..10`).

### Аналіз теорії графів: Інтерпретація довжини шляху(Path Length)

У Neo4j **довжина шляху(`length(p)`)** вимірюється кількістю пройдених **ребер**, а не вузлів.

Оскільки в нашій схемі зв'язок існує лише між Користувачем і Фільмом, будь-який шлях між двома користувачами є неоднорідним і чергується: `(User) - [RATED] -(Movie) - [RATED] -(User)`.

* **1 крок:** Одне ребро `(User)-[:RATED]->(Movie)`. Це неповний шлях, оскільки він веде від користувача до фільму, а не до іншого користувача.
* **Довжина шляху = 2(2 кроки):** `(User A) -> [RATED] ->(Movie X) <- [RATED] <-(User B)`
  * **Інтерпретація:** Прямий збіг інтересів. Користувачі A і B подивилися та оцінили один і той самий фільм `Movie X`.
* **Довжина шляху = 4(4 кроки):** `(User A) ->(Movie X) <-(User B) ->(Movie Y) <-(User C)`
  * **Інтерпретація:** Опосередкований зв'язок(2-й ступінь віддаленості, "друг мого друга"). Користувач A не має спільних фільмів з Користувачем C, але Користувач B є "містком" між ними, оскільки дивився `Movie X` разом з A і `Movie Y` разом з C.
* **Довжина шляху = 6(6 кроків):** `(User A) ->(Movie 1) <-(User B) ->(Movie 2) <-(User C) ->(Movie 3) <-(User D)`
  * **Інтерпретація:** Далекий ланцюг кінематографічних уподобань(3-й ступінь віддаленості). Зв'язок проходить через 3 проміжні фільми та 2 проміжних користувачів. Такий шлях показує, як смаки транслюються через мережу спільних інтересів на великих відстанях.

## Завдання 4: Аналіз супервузлів(Supernodes) та продуктивність

Усі cypher-запити збережено у файлі `queries/part4_supernodes.cypher`.

### Пояснення логіки cypher-запитів
1. **Використання `COUNT {(n)--() }`:** Ця функція віддає кількість ребер за $O(1)$ без реального вичитування і сканування всіх зв'язків з диска/пам'яті.
2. **`coalesce()`:** Використовується для уніфікації виводу, оскільки різні мітки вузлів мають різні назви ідентифікаторів(`title` у `Movie`, `userId` у `User`, `name` у `Genre`).

### Відповіді на архітектурні запитання

#### 1. Які вузли виявилися супервузлами? Скільки у них зв’язків?
У нашому датасеті MovieLens можна виділити три типи супервузлів:
* **Жанрові супервузли(`Genre`):** Вузли жанрів є найбільшими супервузлами. Наприклад, жанр **`Drama`** з'єднаний з кількома тисячами фільмів(`HAS_GENRE`).
* **Популярні фільми(`Movie`):** Топові культові фільми(наприклад, *"American Beauty"*, *"Star Wars"*, *"Jurassic Park"*) мають більше **1000** вхідних ребер `RATED`.
* **Гіперактивні користувачі(`User`):** Окремі профілі користувачів оцінили понад **1000** фільмів.

#### 2. Чому запит, що зачіпає такий вузол, працює повільніше, ніж запит по «звичайному» вузлу з тими самими індексами?

Наявність індексу не рятує від проблеми супервузлів, і ось чому:

**Різниця між Пошуком та Обходом:**
   * **Індекс** працює тільки на першому кроці: він знаходить сам вузол у пам'яті за $O(\log N)$.
   * **Обхід графа** працює за $O(M)$, де $M$ - кількість ребер вузла. Коли запит намагається пройти через супервузол(наприклад, знайти всі фільми жанру Drama: `(m1)-[:HAS_GENRE]->(g:Genre {name:'Drama'})<-[:HAS_GENRE]-(m2)`), база змушена вичитати і перебрати списки суміжності(Relationship Chains) усіх ребер цього жанру.

#### 3. Яку конкретну стратегію з лекцій ви б застосували для цього датасету?(Чи є жанри супервузлами і що з ними робити?)

**Жанрові вузли `Genre` - це класичні супервузли.**

Для оптимізації цього датасету застосовуються такі стратегії боротьби:

1. **Стратегія 3: Денормалізація жанру**
   * Оскільки жанри є статичними метаданими і рідко змінюються, їх доцільно дублювати у вигляді масиву рядків безпосередньо у властивість вузла `Movie`: `Movie {genres: ['Drama', 'Action']}`.
   * **Результат:** Прості фільтрації(*"Знайти фільми жанру Drama"*) виконуються через індекс по масиву без зачіпання супервузла `Genre`. Вузли `Genre` залишають лише для глобального аналізу спільнот в базі данних.

2. **Стратегія 3.1: Денормалізація лічильників**
   * Щоб дізнатися середній рейтинг або кількість оцінок супервузла-фільму(наприклад, *"Star Wars"*), не потрібно щоразу перераховувати кількість ребер. Показники `ratingCount` та `avgRating` підраховуються заздалегідь і зберігаються як властивості вузла `Movie`.

3. **Стратегія 2: Партиціювання за часом супервузла і Стратегія 1: використовувати проміжні вузли-агрегатори**
   * Для дуже великих систем супервузол розбивають на кілька підвузлів за категоріями або часом(наприклад, `Genre_Drama_1990s`, `Genre_Drama_2000s`), що зменшує довжину списку суміжності для кожного конкретного вузла. Використовувати її варто лише тоді, коли запис у базу "лягає" через блокування, або коли ми працюємо з графовим датасетом, де денормалізація(перенесення жанру у властивості фільму) неможлива за умовами бізнес-логіки.
  
4. **Стратегія 4: фільтрація через індекс перед обходом**
   * Покладатися на індексну фільтрацію для порятунку від супервузлів в цьому датасеті - це критична помилка.
    Ми ставимо продуктивність своєї системи в залежність від того, наскільки вузьким буде запит користувача. Якщо фільтр відсіче 99% даних - ми в безпеці. Якщо відсіче лише 50% - база "ляже" на обході супервузла. Це непередбачуване навантаження.

## Завдання 5: 

Усі Cypher-запити для роботи з Graph Data Science збережено у файлі `queries/part5_gds.cypher`.

### 5.1 Запуск алгоритму PageRank через GDS

1. **Матеріалізація зв'язків `CO_RATED`:**
   * Створення прямого графа "Фільм–Фільм" переводить граф `(User)-[:RATED]->(Movie)` у показовий однорідний граф взаємозв'язків кінокартин.
   * Вага ребра `weight` дорівнює кількості користувачів, які оцінили **обидва** фільми на 4 і більше балів.
   * Фільтр `COUNT {(m)<-[:RATED]-() } > 20` відсікає непопулярні фільми, зменшуючи граф до найбільш релевантного ядра.

2. **In-Memory Проєкція(`gds.graph.project`):**
   * GDS працює в оперативній пам'яті(RAM), витягуючи лише необхідну топологію.
   * Ми вказуємо `orientation: 'UNDIRECTED'`, оскільки спільна висока оцінка є симетричним відношенням(якщо фільм А схожий на Б, то й Б схожий на А).

3. **Обчислення PageRank(`gds.pageRank.stream`):**
   * Використовується параметр `relationshipWeightProperty: 'weight'`, завдяки чому алгоритм враховує не просто факт наявності зв'язку, а й **міцність(вагу)** спільної аудиторії між фільмами.

4. **Звільнення ресурсів(`gds.graph.drop` + `DELETE`):**
   * Звільнення RAM після завершення обчислень є обов’язковим етапом життєвого циклу GDS.

### Інтерпретація результатів: Що означає високий PageRank для фільму?

**Високий PageRank у цьому графі - це не лише «найбільш популярний фільм».**

Відмінність між примитивною популярністю та PageRank полягає в наступному:

1. **Просто популярний фільм:**
   * Це фільм, який подивилися мільйони людей. Він має високу кількість ребер `RATED`, але ці оцінки можуть надходити від випадкових користувачів, які не мають глибоких або сформованих кінематографічних уподобань.

2. **Високий PageRank:**
   * Алгоритм PageRank оцінює *'авторитет'*, що передається по ланцюжку. Фільм отримує високий бал не просто за велику кількість зв'язків. Його оцінка зростає лише тоді, коли він тісно пов'язаний(`CO_RATED`) із тими стрічками, які самі вже є визнаними лідерами в цій мережі
   * Якщо користувач високо оцінює фільм із високим PageRank, це з високою ймовірністю означає, що він знаходиться в центрі якісного осередку кіноманів, а не просто випадково переглянутий фільм.
 
### 5.2: Виявлення спільнот алгоритмом Louvain

#### 1. Чи відповідають отримані кластери інтуїтивним групам?
**Так, кластери чітко сегментуються за кінематографічними профілями.** Алгоритм Louvain групує користувачів, максимізуючи метрику *modularity*. Оскільки зв'язки `SIMILAR` базуються на високо оцінених спільних фільмах, щільність зв'язків природним чином формується навколо жанрових уподобань. 
Через обмеження кількості матеріалізованих ребер(через ліміти безкоштовного тарифу) кластеризація охоплює найактивніших користувачів(тих, хто має найбільше спільних фільмів), але загальна жанрова тенденція зберігається.

#### 2. Як ви це перевірили?
Перевірка здійснена  cypher запитом в **кроці 4.2:**

1. Алгоритм `gds.louvain.write` фізично зберіг ідентифікатор спільноти(`communityId`) як властивість кожного вузла `User`.
2. Запит відфільтрував Топ-10 наймасовіших спільнот.
3. Для кожної спільноти було виконано обхід графа: від користувачів цього кластера до фільмів, які вони оцінили $\ge 4.0$, і далі до жанрів цих фільмів.
4. Функція `count(r)` підрахувала частоту кожного жанру всередині конкретного кластера, а `collect(genre)[0..3]` вибрала топ-3. 
5. Різний набір цих топ-3 жанрів для різних `communityId` є математичним підтвердженням того, що алгоритм розбив людей саме за інтересами, а не випадковим чином.

## Завдання 5.3: Найкоротший шлях за алгоритмом Дейкстри та феномен «Тісного світу»

1. **Метрика масивної ваги(`relationshipWeightProperty`):**
   * У даній проєкції властивість `weight` відповідає кількості спільних високооцінених фільмів. 
   * Стандартний алгоритм Дейкстри інтерпретує `weight` як **вартість/відстань**(Cost/Distance), тому він шукає шлях із найменшою сумарною вагою. Якщо бізнес-завдання вимагає пошуку шляху через "найсильніші" зв'язки, вагу ребра інвертують($1 / \text{weight}$), проте для оцінки топологічної зв'язаності достатньо класичного пошуку шляху.

2. **Формат виводу `pathUserIds`:**
   * Запит витягує масив ідентифікаторів вузлів `nodeIds` і за допомогою Cypher List Comprehension перетворює внутрішні ID Graph Data Science на реальні `userId` користувачів.

### Аналіз топології: Відповіді на питання

#### 1. Наскільки «тісний світ» у цьому датасеті?
Датасет MovieLens демонструє виражені властивості **мережі «Тісного світу»(Small-World Network)**. 

* **Причина:** У системі є культові фільми та гіперактивні користувачі(супервузли). Вони виступають в ролі "глобальних мостів".
* **Практичний результат:** Будь-які два випадково обрані користувачі з'єднані між собою через дуже коротку ланцюгову послідовність спільних інтересів. Навіть при жорсткому обмеженні кількості зв'язків у графі, ізольованих кластерів практично немає.

#### 2. Яка середня довжина шляху? Чи підтверджується гіпотеза «шести рукостискань»?
**Гіпотеза «шести рукостискань»(Six Degrees of Separation) не просто підтверджується, а перевищується:**

* **Середня довжина шляху:** Для більшості пар користувачів найкоротший шлях у графі становить всього **2–3 кроки**.
* **Інтерпретація:** Довжина шляху $= 2$ означає, що користувачі A і B безпосередньо не пов'язані, але мають спільного "сусіда", який поділяє кінематографічні смаки з обома. 
* **Висновок:** Граф рекомендаційної системи має значно вищу щільність і коротший діаметр, ніж класичні соціальні мережі, оскільки смаки людей зосереджені навколо обмеженої кількості популярного контенту.

## Частина 6: Архітектурний аналіз

### 1. Граф vs SQL
SQL ідеально працює з таблицями, але затикається на глибоких зв'язках. Наприклад, для фільтрації(Запит 5) або найкоротшого шляху(Запит 6) у SQL довелося б багато разів з'єднувати гігантську таблицю оцінок саму із собою через важкі операції `JOIN`. Це викликає вичерпання пам'яті. У графі зв'язки прокладені фізично, тому база просто проходится по них, виконуючи запит за мілісекунди.

### 2. Де граф програє
Граф погано підходить для глобальної аналітики, де треба просканувати всю базу даних цілком. Для побудови статистичних звітів(наприклад, середній вік усіх користувачів системи) або масового вивантаження даних краще підійде класична реляційна база. Граф при таких задачах змушений перебирати мільйони вузлів, що працює вкрай повільно.

### 3. Покращення схеми
Щоб прискорити систему, схему потрібно денормалізувати під конкретні запити:
* **Для Запиту 1(Фільми за жанром):** Перенести жанри безпосередньо у властивості фільму як масив(наприклад, `genres: ['Action']`) і там само зберігати вже порахований середній рейтинг. Це дозволить знаходити потрібні фільми миттєво, не прораховуючи тисячі ребер оцінок на льоту.
* **Для Запиту 4(Аналітика жанрів):** Створити пряме узагальнене ребро від Користувача одразу до Жанру(наприклад, `[:LIKES_GENRE]`). Це дозволить аналізувати смаки людей безпосередньо, повністю оминаючи проміжні вузли конкретних фільмів.
